# wiki-kit — Architecture

Four layers, strictly separable: the **per-repo wiki** (the data), the **kit**
(schema + tooling + skills, one repo, reused everywhere), the **export
surfaces** (claude.ai Projects), and the **harbor federation** (the home
inference system's knowledge substrate). Each lower layer is useful without the
ones above it — if harbor integration never ships, the wikis still pay for
themselves. That is a design requirement, not an accident.

## 1. Per-repo wiki (the data layer)

```
<repo>/
├── CLAUDE.md            # gains the standard wiki stanza (SPEC §8)
└── wiki/
    ├── INDEX.md         # one line per page — the only always-read file
    ├── wiki.toml        # repo name, visibility, cap overrides
    ├── manifest.json    # GENERATED by wiki-lint; never hand-edited
    └── pages/
        ├── <id>.md      # one page = one question a future agent would ask
        └── ...
```

Pages are plain markdown, Obsidian-compatible (same convention as
hearth-vault), with restricted-grammar frontmatter (SPEC §2) and `[[id]]`
links. The wiki lives *in the repo, in git* — versioned, diffable, visible to
every agent and collaborator, no side database. `manifest.json` is a build
artifact committed for consumers' convenience; `wiki-lint` regenerates it
deterministically and CI fails if it's out of date (same pattern as a
lockfile).

### The freshness loop (load-bearing)

Agent-written docs rot invisibly; that's why they usually aren't worth having.
The wiki closes the loop mechanically:

1. Every page declares `sources:` (paths, optionally `#fragment`-annotated) and
   `verified: {commit, date}` — the evidence its claims rest on.
2. `wiki-lint` computes candidate staleness as
   `git diff --name-only <verified.commit>..HEAD` ∩ `sources` (prefix match).
   No LLM involved; it's a set intersection.
3. `/wiki-verify` (agentic) re-reads only candidate-stale pages against current
   code and either re-stamps `verified` or flips `status: stale` (or fixes the
   page, or deletes it). Stale pages stay retrievable but are marked in INDEX
   and down-rankable by any consumer.

This split — *detection* is deterministic and cheap, *adjudication* is agentic
and targeted — is what makes a 60-page wiki maintainable in minutes a week.

### Knowledge flow during normal work

```
work session ──> /wiki-update distills:
                   new gotcha? decision digest? corrected assumption?
                   ├── belongs in code/docs/dispensa?  → put it THERE, wiki gets a pointer at most
                   ├── already covered?                → update that page (or nothing)
                   └── else                            → new page + INDEX line
reading path:    CLAUDE.md stanza → INDEX.md → open only the pages that match the task
```

The routing question ("does this belong here?") is the same discipline as the
auto-memory system's "don't save what the repo already records" — inverted:
don't wiki what deserves to be normative. Tonight's adversarial reviews found
real drift bugs between *deliberately* parallel-authored docs; a wiki that
restates spec constants would manufacture that bug class continuously. Hence
the hard rule: **wiki pages point at normative artifacts, never restate their
values.**

## 2. The kit (one repo: `ricettario`)

A Claude Code plugin plus a small deterministic tool:

```
ricettario/
├── plugin/
│   ├── skills/
│   │   ├── wiki-init/       # bootstrap a repo: survey → seed pages → INDEX → stanza
│   │   ├── wiki-update/     # post-work distillation (the everyday verb)
│   │   ├── wiki-verify/     # adjudicate candidate-stale pages
│   │   ├── wiki-gc/         # merge, split, prune, re-link; enforce caps
│   │   └── wiki-export/     # build PROJECT-DIGEST.md for claude.ai Projects
│   └── plugin.json
├── bin/wiki-lint            # Python 3, stdlib-only (SPEC §6) — schema, links,
│                            #   caps, staleness compute, manifest emit
├── templates/               # page-kind templates + wiki.toml + CLAUDE.md stanza
├── schema/wiki-manifest.v1.schema.json
└── fixtures/                # a golden mini-wiki: lint round-trip + staleness cases
```

Why a plugin, not per-repo copies: skills and lint evolve; N repos must not
fork the discipline. Repos own only their *data* (`wiki/`); behavior updates
land once in ricettario. `wiki-lint` is vendorable into CI via a pinned
checkout or a copy-on-init with a version stamp — SPEC §6 fixes the
determinism contract so versions interoperate.

Why stdlib-only Python for lint: the frontmatter grammar is deliberately
restricted (SPEC §2.1) so a ~60-line parser suffices — no YAML dependency, no
environment drift across eleven repos and CI. Deterministic output ordering
makes `manifest.json` diffs meaningful.

## 3. Export surfaces (claude.ai Projects)

Two paths, chosen per project:

- **GitHub-synced projects** (preferred): the Project syncs the repo; `wiki/`
  pages are directly usable project knowledge. Zero extra machinery; freshness
  equals sync freshness.
- **`/wiki-export`** for projects without a synced repo: concatenates
  `INDEX.md` + all `status: current` pages into one `PROJECT-DIGEST.md`
  (size-capped, manifest-stamped with repo + commit + date so a stale upload is
  self-identifying). Tony uploads it; regenerating is one command. Digest
  includes only pages whose effective visibility permits the destination
  (SPEC §5) — mechanically enforced, same rule as everywhere else.

## 4. Harbor federation (the home inference mesh)

Grounded in the harbor artifacts (`DATA-CONTRACTS.md` Rev B, ARCHITECTURE
§§ vault/indexer): harbor's curated-knowledge plane is **hearth-vault** —
Obsidian-compatible markdown, agent edits only via PR (`propose_edit`, never
main), chunked and embedded into pgvector by the brain's indexer, retrieval
via `home/embed` + `home/rerank`, trust `trusted` *because the PR gate earns
it* (DATA-CONTRACTS §F).

A wiki-kit wiki is the same artifact class with the same discipline, so the
mesh is a federation, not a bridge:

**Each repo wiki is a read-only vault shard.** Harbor's indexer grows one
source type, `repo-wiki`, configured with a list of manifest locations
(local checkouts or git remotes). It ingests via `manifest.json`:

- **Incremental re-embedding for free:** stable page `id`s + `hash`
  (sha256 of body) — re-chunk/re-embed only changed pages. Heading-structured
  pages (SPEC §3 caps) chunk cleanly.
- **Namespace routing from visibility:** manifest `visibility` maps to harbor
  namespaces — public repos (skimmer, propagation) → `shared:family`-safe;
  closed repos (cqdx) → `private:argus`. The private global index MAY hold
  closed-repo knowledge (it's argus-scoped); the open/closed rule constrains
  *copying between repos*, which federation never does — harbor reads, it
  doesn't replicate content into other wikis.
- **Trust mapping is harbor's policy, wiki-kit's data:** the manifest carries
  `maintainer` (human/agent/mixed) and `status` per page. Recommended harbor
  default: repo-wiki pages ingest as `trusted` (they live in operator-reviewed
  git history — the commit gate is argus's PR gate), with `status: stale`
  pages down-ranked or excluded, and a per-repo override if some repo's wiki
  is ever loosely reviewed. The decision sits in harbor's indexer config, not
  in wiki-kit — producer describes, consumer decides.
- **Write-back follows INV-3's pattern:** harbor agents never write repo wikis
  directly; a harbor-side improvement becomes a PR against the repo (exactly
  `vault.propose_edit`). Claude Code agents in-repo write directly — they're
  in the operator lane, and lint + commit review is their gate.

Direction of dependency: wiki-kit knows *nothing* about harbor beyond keeping
the manifest self-describing and versioned (`wiki-manifest/v1`). Harbor's
indexer depends on the manifest schema. If harbor's design shifts, the
federation config changes; the eleven wikis don't.

## 5. What lives where — the full knowledge map

| Knowledge | Home | Consumed via |
|---|---|---|
| How code works, why decisions were made, gotchas | repo `wiki/` | INDEX → pages; harbor `repo-wiki` shards |
| Normative specs, constants, contracts | repo `docs/`, `dispensa` | cited by wiki, never restated |
| Cross-repo obligations | `dispensa` Q/ADR | wiki pages reference ids |
| Family/life knowledge, preferences, episodes | harbor `memory_fact` / `episode` | harbor brain only |
| Curated family documents | hearth-vault | harbor vault tools |
| Who Tony is, workflow preferences | Claude auto-memory | session bootstrap only |
| Untrusted clippings | Karakeep | quarantined, harbor-side |

The wiki deliberately does not touch rows 4–7. One new box, clean edges.
